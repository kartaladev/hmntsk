## Context

See proposal.md — Why. The sink today (`delivery/redis/redis.go`) sends `XADD <stream> * <fields>` with nothing else set on `goredis.XAddArgs`, validates its options in `New`, and never dials. The pinned client, go-redis v9.22.0, already exposes `MaxLen`, `MinID`, `Approx`, `Limit` and `Mode` on `XAddArgs`, and emits them as `XADD key [mode] [MAXLEN|MINID ~ threshold] [LIMIT n] * ...`. The tests pin `redis:8.2.9-alpine`.

Broker behaviour below was measured during exploration on `redis:8.2.9-alpine` and `redis:7.4.7-alpine`, using go-redis's argument order:

| Setup | Observed |
|---|---|
| no mode, group read 1–4 unacked, `MAXLEN ~ 3` (node size 1) | stream `5 6 7`; group still lists 4 pending IDs; reading them back returns IDs with no fields |
| `DELREF`, same | stream `5 6 7`; pending count 0 |
| `ACKED`, group acked 1–2 of 6 | stream `3 4 5 6 7`: stops at the first unacknowledged entry |
| `ACKED`, a group that never read | after 5 more publishes with `MAXLEN ~ 3`: length 11 |
| `ACKED`, no groups | trims to the bound |
| any mode keyword, including `KEEPREF`, on 7.4.7 | `ERR Invalid stream ID specified as stream command argument` |
| no mode, `MAXLEN ~` / `MINID ~`, on 7.4.7 | accepted |
| `MAXLEN ~ 10` on 251 entries, default `stream-node-max-entries` 100 | length 51 |
| `MAXLEN ~ 5` on 21 entries, `stream-node-max-entries` 1 | length 5 |
| `MAXLEN ~ 10` on 500 entries, `stream-node-max-entries` 1, two publishes | length 401, then 302 |
| `MAXLEN ~ 10` on 3000 entries, `stream-node-max-entries` 10 | length 2001 |

## Goals / Non-Goals

**Goals:**

- A host can bound the stream by length or by age, on the publish path, with no extra round trip.
- A host on Redis 8.2+ can protect consumer groups from losing unacknowledged entries, explicitly.
- Nothing about an unconfigured sink changes, including which Redis versions it works on.
- Every operational hazard the options introduce is written down where an operator will read it, and a test fails if the document and the code drift apart.

**Non-Goals:**

- **Exact trimming (`=`).** Decided: always `~`. Exact trimming costs node rewrites on every publish inside a relay pass, and no requirement needs exactness.
- **Exposing `LIMIT`.** Redis's implicit effort cap is kept; see D6.
- **A startup capability probe** (a `Sink` method that checks the server version or trial-trims a scratch key). It is the only way to catch a trim mode on an old broker before publishing starts, but it adds API and a key the sink would own, against the producer-only line. The failure it would catch is documented instead; a probe can be added later without breaking anything.
- **Standalone `XTRIM`, scheduled trimming, or retention for dead letters.** Unrelated to the write path.
- **Idempotent production (`IDMP`).** Noted during exploration as a way to let the broker drop redeliveries; a separate change.

## Decisions

### D1. Trim on `XADD`, not in a separate command

The bound rides on the publish the sink already sends. A separate `XTRIM` would double the round trips per event, open a window where the write succeeded and the trim did not, and need its own timeout and error classification.

_Alternative:_ a host-driven `Trim(ctx)` method. Rejected for this change: it hands the host a job to schedule, which is the gap this change exists to close.

### D2. Length and age as two options, mutually exclusive

`WithMaxLen(n int64)` sets `MaxLen`; `WithMaxAge(d time.Duration)` sets `MinID`. Redis accepts one threshold per command and go-redis silently prefers `MaxLen` when both are set, so `New` rejects the combination rather than letting one quietly win.

_Alternative:_ a single `WithRetention(Retention)` value type. Rejected: two options match the sink's existing one-knob-per-option style and read better at the call site.

### D3. The age cutoff is `clock.Now() - maxAge` in milliseconds, as `<ms>-0`

Stream IDs generated by `*` are the broker's millisecond time. The cutoff is computed per publish from a `hmntsk.Clock`, supplied with `WithClock`, defaulting to the system clock — the same port and option name the webhook sink already uses.

The cutoff uses the host's clock while entry IDs use the broker's. Skew between them shifts the effective retention by the skew. That is accepted and documented: the approximation already makes the bound "at least", and NTP-level skew is small against any realistic retention window.

_Alternative:_ read the broker's time with `TIME` before each publish. Rejected: an extra round trip per event to correct an error smaller than the approximation.

### D4. `TrimMode` is a string type with three constants, and its zero value sends nothing

```go
type TrimMode string

const (
	TrimKeepRef TrimMode = "KEEPREF"
	TrimDelRef  TrimMode = "DELREF"
	TrimAcked   TrimMode = "ACKED"
)
```

The zero value leaves `XAddArgs.Mode` empty, so go-redis emits no mode keyword. That is load-bearing, not cosmetic: Redis 7 rejects even `KEEPREF` — the 8.2 default — so defaulting to an explicit `TrimKeepRef` would break every host on Redis 7 that sets only a bound.

`New` rejects any value other than the three constants, and rejects a mode with no bound (the mode would be sent to the broker with nothing to trim, which is meaningless and still fails on Redis 7).

_Alternative:_ an int enum with `String()`. Rejected: the value is sent to the broker verbatim, and a string type keeps the constant and the wire value the same thing.

### D5. A mode rejected by the broker stays retryable

The existing requirement classifies every broker rejection as retryable, and this change does not carve out an exception. Telling a syntax error on an old server apart from an operational rejection would mean matching Redis error strings, and the text is not specific to trim modes (it is "Invalid stream ID"). A permanent verdict here would also dead-letter the backlog immediately rather than after the attempt limit, which is worse.

The consequence — a moded sink on Redis < 8.2 publishes nothing and eventually dead-letters its backlog — is the first operational constraint documented (D7), with the exact error text so an operator searching for it finds the explanation.

### D6. Approximate trimming, and what "approximate" means in numbers

`Approx` is always true. With `~`, Redis removes whole radix-tree nodes, each holding up to `stream-node-max-entries` (default 100) entries, so the stream can sit up to about one node above the bound (observed: `MAXLEN ~ 10` kept 51 of 251). Redis also caps the entries one `~` trim will examine at a default limit. The sink leaves `Limit` at zero, which omits `LIMIT` and keeps Redis's default.

That cap matters for a host enabling a bound on an existing, already-huge stream: each publish trims at most the capped amount, so the backlog shrinks over many publishes rather than on the first. The default is 100 × `stream-node-max-entries`, measured on the pinned image: with a node size of 1, a 500-entry stream under `MAXLEN ~ 10` went to 401 and then 302 over two publishes; with a node size of 10, 3000 went to 2001. `MINID ~` and `ACKED` hit the same cap. At the default node size that is 10,000 entries per publish.

### D7. Operational constraints live in `docs/delivery.md`, guarded by a test

A new top-level section in `docs/delivery.md` — after the webhook sections, matching their "contract, not illustration" register — covers the Redis stream contract and its retention options. It states, at minimum:

1. Any trim mode requires Redis 8.2+; on an older server every publish fails with `ERR Invalid stream ID specified as stream command argument`, retries, and dead-letters after the attempt limit. A bound without a mode works on any version. Check the server version before setting a mode.
2. Without a mode, or under `KEEPREF`, trimming removes entries a consumer group has not read or acknowledged; their IDs stay pending with no content, and consumer code must tolerate a pending entry whose body is gone.
3. `DELREF` removes those pending IDs too, so a consumer never learns an entry was lost.
4. `ACKED` stops at the first entry any group has not acknowledged. One stale or abandoned group stops trimming entirely and the stream is unbounded again. Delete groups you no longer run, and monitor stream length.
5. `ACKED` with no groups behaves like no mode.
6. Approximate means "at least the bound", overshooting by up to one node (`stream-node-max-entries`).
7. The age bound uses the sink's clock against broker-generated IDs; skew shifts retention by the skew.
8. Enabling a bound on a large existing stream trims gradually, capped per publish.

`delivery/redis/docs_test.go`, mirroring the webhook's, asserts the section names every `TrimMode` constant's wire value, the minimum version `8.2`, and the exact Redis 7 error text. The error text is also asserted against a real Redis 7 container (task 4.3), so the document cannot quote an error the broker no longer produces.

The package doc gains a short retention paragraph pointing to that section; README's Redis row mentions optional retention.

### D8. Deterministic tests via server configuration on the shared helper

Approximate trimming is only exact when `stream-node-max-entries` is 1. Rather than a second container helper, `RunTestRedis` gains a `TestOption` that applies `CONFIG SET` pairs after the ping, per the `use-testcontainers` rule of one helper per service. Retention tests run in their own suite with that option; the existing `publishSuite` is untouched.

Age tests seed entries with explicit IDs relative to a fixed clock set to the current time (so the publish's own `*` ID lands after the seeded ones), then publish and read the stream back. Redis 7 cases reuse the same helper with `WithTestImage` and a pinned `redis:7.4.7-alpine`.

## Risks / Trade-offs

- [A trim mode on Redis < 8.2 stops all publishing and dead-letters the backlog] → Documented with the exact error text; zero-value mode sends nothing; construction rejects a mode with no bound. A startup probe is an explicit non-goal, addable later.
- [`ACKED` plus a stale group silently removes the bound] → Documented, with the remedy (delete dead groups, monitor `XLEN`). The spec scenario and a container test pin the behaviour so it is not mistaken for a bug later.
- [Trimming without `ACKED` loses unread entries] → This is what a bound means; documented, and the mode exists precisely so a host can choose otherwise.
- [Host/broker clock skew under the age bound] → Documented; small against realistic windows.
- [The Redis 7 test adds a second image pull to CI] → One pinned image, used by a handful of cases in the same module's integration job.
- [go-redis emits mode before `MAXLEN`, while Redis docs show it after] → Measured on 8.2.9: both orders are accepted. The container tests exercise go-redis's actual order.

## Migration Plan

Additive and opt-in. An existing host sees no change until it sets an option. Rollback is removing the option; entries already trimmed are gone, which the docs state.
